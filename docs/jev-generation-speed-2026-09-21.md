# Jev 与行程生成提速验证

分支：`codex/jev-generation-speed`。基线：`1e78e9f`。测试日期：2026-09-21（America/Los_Angeles）。未部署到生产。

## 已实现

- 新增经过现有鉴权和限流的 `/api/jev` 候选评分请求；只接受最多 64 个不重复 ID，不接受客户端自定义评估问题。校验返回分数范围、完整性和 ID；失败保留旧推荐流程，行程筛选失败则保留原候选。
- 添加地点：按分类、酒店、日期上下文、偏好和语言维护内存候选队列。排除已在行程和已展示地点；首次批量评分，换一批消费剩余队列，剩余不足时后台补充。队列 10 分钟过期、最多 12 个上下文，关闭窗口和卸载时取消；换批失败不先清空旧卡片。
- 推荐卡片先使用已验证名称、地址、评分和距酒店距离。没有等待模型编写长篇推荐理由；缺失事实不补造。
- 行程：Jev 筛选候选，主模型输出短候选 key、顺序、时间、简短活动等；应用从候选恢复名称、来源 ID、地址。保留原航班/日期/偏好规则及角色约束，不用 Jev 替代完整排程。
- 有真实候选坐标的地点先生成可用路线；Google/Tripadvisor 详情和图片最多 3 个并行在后台补齐。没有真实坐标时仍等待原地点解析。晚到的补全只能合并到原占位对象，不能复活已删除地点或覆盖用户编辑；保留已验证坐标。
- 全部行程仍优先第一天、最后一天按原规则串行，中间日期由两个 worker 连续处理并逐天发布。并行日景点冲突时，以已发布日为准重排，最多两次；断点记录只推进到连续完成的日期。后台 worker 失败后不再发布其他晚到结果。
- 内存阶段计时只记录任务名、阶段、版本和毫秒数，不记录提示词、密钥或用户行程。

## 测试方法和边界

真实调用现有 DeepSeek V4.1 Flash、Vercel AI Gateway Jev、地点和图片接口。通过 Vite SSR 加载应用实际服务函数及实际本地 API 代理，没有模拟模型响应。Node 进程使用独立内存存储，没有读取或覆盖用户保存的行程。

固定公开测试酒店 Hôtel Paris France、2026-10-12 起的行程、默认偏好、中文。两组使用完全相同的 49 个真实候选（咖啡馆 15、餐厅 15、景点 19）。推荐测试使用其中 15 家咖啡馆，连续选三批，每批 4 家。单日测试为三日游中的第 2 天；全程测试为五日游，无迪士尼日。使用同一冻结候选池，是为了将候选查询波动与模型/排程改动分开。

**这些是服务层 A/B 数据，不是手机端点击到绘制的端到端数据。** 不包含首轮候选获取、浏览器渲染和手机网络；每个样本启动独立进程，应用地点缓存初始为空，但不能清除上游提供方缓存。每种场景/版本取 3 个成功样本的中位数，交错先后顺序。模型输出具有随机性，不能将小样本结果当成生产 SLA。

基线保留旧推荐、完整 JSON、阻塞详情以及两天一批发布的路径。优化版包含候选评分、精简输出、资料后台加载、持续并发和冲突重排，是组合优化对比，**不能把行程的全部收益归因于 Jev**。原版不足 4 个时的 UI 补齐请求未在基准脚本中重演；这批基线每次均已返回 4 个，不影响本次结果。背景“补充新候选”另由单元测试覆盖，本次队列已有足够候选。

## 结果

| 指标（中位数） | 基线 | 优化版 | 等待减少 |
| --- | ---: | ---: | ---: |
| 首批推荐完整可用 | 4.168 s | 0.376 s | 91.0% |
| 第一次换一批 | 6.405 s | <1 ms（队列命中） | 无新模型等待 |
| 第二次换一批 | 5.213 s | <1 ms（队列命中） | 无新模型等待 |
| 单日可用路线 | 6.289 s | 2.608 s | 58.5% |
| 单日含后台资料处理完成 | 6.289 s | 5.582 s | 11.2% |
| 五天路线全部可用 | 21.573 s | 11.274 s | 47.7% |
| 五天含后台资料处理完成 | 21.573 s | 13.428 s | 37.8% |

“<1 ms”是本地队列函数的测量分辨率，不代表用户实际感受到零毫秒。候选耗尽、上下文变化或缓存过期会重新查询和评分。后台处理完成指接口尝试结束，并不保证每个官网都有可用图片；测试遇到的第三方网站证书错误按现有策略保留备用图片，没有绕过 TLS 检查。

最终样本：

- 推荐：基线首批 4168 / 3939 / 4518 ms；优化版 428 / 376 / 352 ms。
- 单日路线：基线 7190 / 5554 / 6289 ms；优化版 2624 / 2355 / 2608 ms。
- 五天路线：基线 21573 / 20605 / 25138 ms；优化版 10838 / 11274 / 11604 ms。
- 五天优化版首日分别在 2288 / 2001 / 2311 ms 可用；其余日完成后陆续出现。

## Jev 可靠性与质量检查

- 首次推荐试跑遇到一次 Gateway 503，作为失败样本单独保留，未伪装成成功结果。之后三次推荐评分成功，三批各 4 个，共 12 个不重复的候选。
- Jev 行程筛选仍不稳定：最终三次单日均触发回退；三次全程各有 2 次评分成功、5 次回退（含跨天冲突重排）。因此这次单日的提速主要来自精简输出和后台补全，不能宣称已证明 Jev 行程筛选比不筛选更快。
- 尝试过小批次和不同判断形式，仍遇到 503；没有证据把故障确定归因于候选数量。最终保留原批量评分接口和回退策略，没有静默更换模型。
- 五天的三个最终优化样本均有 5 天，首日有酒店入住、非末日回酒店、末日有机场；跨天没有重复地点。原版三个样本存在中间日期重复景点，优化版通过重排消除，没有只为速度保留重复结果。
- 以上是结构/来源检查，不等同于完整路线质量、人类偏好匹配或营业时间准确率评估。测试没有真实航班约束，不宣称覆盖所有到离时间组合；仍需在不同酒店、偏好、语言和真实航班上扩大验证。

## 复现

保留了公开候选快照和原始计时/路线输出：

- `docs/benchmarks/jev-candidates-2026-09-21.json`
- `docs/benchmarks/jev-generation-2026-09-21.json`

需要项目现有服务端 API 凭据；脚本不会输出凭据。每次执行会发生真实接口调用。

```sh
BENCH_VARIANT=baseline BENCH_SCENARIO=recommend BENCH_FIXTURE=docs/benchmarks/jev-candidates-2026-09-21.json BENCH_OUT=/tmp/baseline.json node scripts/benchmark-generation.mjs
BENCH_VARIANT=fast BENCH_SCENARIO=recommend BENCH_FIXTURE=docs/benchmarks/jev-candidates-2026-09-21.json BENCH_OUT=/tmp/fast.json node scripts/benchmark-generation.mjs
```

将 `BENCH_SCENARIO` 改为 `day` 或 `all` 可验证单日或五天任务。脚本使用本机 5186 端口，完成后关闭。应用本身默认启用优化路径；启动时设 `VITE_GENERATION_VARIANT=baseline` 可切回旧路径进行对照。分支未合并、未推送、未部署。
